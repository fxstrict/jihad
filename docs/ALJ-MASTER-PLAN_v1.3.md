# 1. الغرض وقاعدة الحقيقة

هذا الملف هو دفتر المشروع الدائم الذي يرفق مع كل حساب Claude جديد. يجب أن يمنع تكرار التخطيط من البداية، ويبيّن المنتج المتفق عليه، والقرارات الثابتة، وحالة التنفيذ الحقيقية، والمهمة التالية الوحيدة.

**لا يعتبر أي بند مكتملًا** لمجرد كتابة تقرير، أو إنشاء مجلد/ملف فارغ، أو كتابة واجهة شكلية، أو كتابة اختبار لم يُشغّل، أو قول إن البناء/النشر نجح دون دليل. يجب التفريق بين: تصميم موثق، كود مكتوب، كود اختُبر، بناء ناجح، نشر فعلي، وقبول وظيفي.

الحالات المسموح بها:
- **لم يبدأ**
- **قيد التنفيذ**
- **منفذ — غير مختبر**
- **مختبر — ناجح**
- **مكتمل بدليل**
- **محجوب**
- **ملغى بقرار موثق**

لا يغيّر Claude الحالة إلى «مكتمل بدليل» إلا مع ذكر الملفات والأوامر والاختبارات والنتائج وأدلة البناء/النشر حيث تنطبق.

# 2. تعريف المنتج النهائي

«الجهاد» منصة عربية لإدارة دورة عمل المدرس الخصوصي يوميًا، وليست مجرد جدول حصص. تجمع إدارة المدرس والطلاب وأولياء الأمور والمواد والمراحل والمجموعات والجدول والحصص والأماكن والانتقالات والتذكيرات والحضور والمنهج والواجبات والاختبارات والنتائج والتقارير، مع عمل محلي دون إنترنت ومزامنة آمنة عند توفره، ونسخ احتياطي واستعادة، وصلاحيات وترخيص وبوابة ولي الأمر.

## 2.1 دورة العمل المحورية
1. يفتح المدرس التطبيق ويرى جدول اليوم والحصة التالية.
2. يرى وقت الاستعداد والتحرك والمكان.
3. يفتح الطالب/المجموعة والمادة.
4. يسجل الحضور وما تم شرحه والواجب والملاحظات.
5. ينهي الحصة، وتحفظ البيانات محليًا فورًا.
6. تتحدث التذكيرات والسجلات ذات الصلة.
7. تُزامن التغييرات لاحقًا دون تكرار عند عودة الاتصال.
8. يرى ولي الأمر البيانات المصرح بها فقط بعد تحقق صلاحياته.

## 2.2 المستخدمون المستهدفون
- V1: مدرس خصوصي/مالك منشأة صغيرة.
- التوسع: عدة مدرسين ومساعدون وسكرتير ومحاسب ومركز تعليمي.
- ولي الأمر: حساب واحد لأكثر من ابن.
- الطالب: حساب محدود مستقبلًا إن اعتمد ذلك بقرار نطاق.

# 3. كتالوج الخصائص الكامل

القائمة التالية تصف المنتج المستهدف، وليست ادعاءً بأن كل خاصية موجودة في الكود الحالي.

## 3.1 إعداد المنشأة والإقلاع
- معالج إعداد أول تشغيل، وبيانات المالك والمدرس والمنشأة.
- مفهوم Organization/Workspace من البداية حتى لو كان مدرسًا واحدًا.
- فصل الشخص والحساب والمنشأة والدور والصلاحية والعلاقة والتثبيت والجهاز والترخيص.
- حالات bootstrap واستئناف بعد الانقطاع.
- اكتشاف المنشأة الموجودة ومنع إنشاء منشأة مكررة أو الكتابة فوق بياناتها.
- فحص صحة التطبيق والتخزين والاتصال والمزامنة والترخيص.
- إعدادات قابلة للتغيير بدل القيم الثابتة المنتشرة.

## 3.2 الحسابات والأدوار والصلاحيات
- أدوار Owner, Teacher, Assistant, Secretary, Accountant, Administrator, Parent، وStudent مستقبلًا.
- صلاحيات دقيقة لكل عملية؛ إخفاء الأزرار وحده ليس حماية.
- تحقق موثوق في الخادم للعمليات الحساسة.
- المساعد لا يحصل تلقائيًا على الماليات أو إعدادات الترخيص.
- السكرتير يدير التسجيل والمواعيد والتواصل ضمن صلاحيات محددة.
- المحاسب يدير الماليات دون تعديل المحتوى الأكاديمي افتراضيًا.
- سجل تدقيق للعمليات الحساسة.
- عزل المنشآت ومنع الوصول المتبادل.

## 3.3 الطلاب والأهل والتسجيل الأكاديمي
- إضافة/عرض/تعديل/بحث/تصفية/أرشفة الطلاب، وصورة اختيارية وبيانات أساسية ومدرسة وملاحظات.
- ربط الطالب بولي أمر أو أكثر وفق النموذج المعتمد.
- حساب ولي الأمر يمكنه رؤية عدة أبناء.
- فصل بيانات الاتصال الضرورية عن البيانات الأكاديمية.
- `Academic Enrollment` مؤرخ للمرحلة والصف؛ لا يمحى التاريخ عند انتقال الطالب.
- تسجيل الطالب في مواد متعددة.
- سجل الطالب: الحصص والحضور والمنهج والواجبات والنتائج.
- إدارة دعوة ولي الأمر وتفعيل وصوله وإلغاؤه واستعادته بأمان.
- فصل الملاحظات الداخلية عن الملاحظات المرئية لولي الأمر.
- منع وصول ولي الأمر إلى طالب غير مرتبط به حتى لو غيّر المعرّف في الطلب.

## 3.4 المواد والمراحل والمنهج
- المواد والمراحل والصفوف كيانات منفصلة.
- ربط الطالب بمواد متعددة.
- منهج لكل مادة وسياق أكاديمي.
- تقسيم المنهج إلى وحدات وموضوعات.
- تسجيل ما تم شرحه بكل حصة.
- حساب المنجز والمتبقي ونسبة الإنجاز لكل طالب ومادة وفترة.
- الاحتفاظ بالسياق التاريخي الذي كانت الحصة تعمل وفقه.

## 3.5 المجموعات
- إنشاء مجموعة وربطها بمادة ومدرس وجدول ومكان.
- عضوية تاريخية للطالب: انضمام/انسحاب/انتقال.
- الحصة الفردية والجماعية تستخدمان نموذج Lesson موحدًا.
- تسجيل حضور كل مشارك، لا حالة الحصة وحدها.
- تقارير المجموعة والحضور والمنهج والنتائج.

## 3.6 الحصص والجدول
- إنشاء حصة فردية أو جماعية مع المدرس والمادة والمشارك والتاريخ والوقت والمكان والحالة.
- حالات مضبوطة: مجدولة، بدأت، مكتملة، ملغاة، أعيدت جدولتها.
- فصل قاعدة الجدول المتكرر `Schedule Rule` عن الحصة الفعلية `Lesson Instance`.
- قواعد تكرار أسبوعية واستثناءات.
- كشف التعارضات الزمنية والمكانية.
- إعادة الجدولة والإلغاء دون محو التاريخ.
- التمييز بين تعديل حصة واحدة وتعديل القاعدة أو الحصص المستقبلية.
- حفظ `ScheduleRuleVersionSnapshot` حيث يقتضي المرجع المعماري.
- عرض يومي وأسبوعي وفلاتر بالمدرس والمادة والمجموعة والمكان.

## 3.7 الأماكن والانتقال والتخطيط اليومي
- أماكن: منزل طالب، منزل المدرس، سنتر، مقر، مكان خاص، Online.
- الاسم والعنوان والمنطقة والإحداثيات الاختيارية والنوع والملاحظات.
- محرك انتقال منفصل عن الجدول.
- تقدير زمن الانتقال، وقت الاستعداد والتحرك، وكشف التنقلات الصعبة.
- Daily Planner يجمع الحصص والانتقال والفراغ والمهام والتذكيرات.
- Availability Engine لتحديد الأوقات المتاحة.
- Google Maps تكامل اختياري لا شرط لتشغيل الأساس.

## 3.8 لوحة التحكم والواجهة
- لوحة «اليوم» هي نقطة البداية.
- الحصة القادمة ووقتها ومكانها ووقت التحرك.
- الجدول الزمني والفراغات والتنبيهات والمهام.
- إجراءات سريعة لإضافة طالب وتسجيل حضور وفتح حصة وواجب وملاحظة.
- بحث عام عن الطالب والمجموعة والحصة والمادة.
- عربية RTL، هاتف أولًا، تصميم فاتح حديث وأيقونات واضحة.
- حالات تحميل/فراغ/خطأ/انقطاع اتصال مفهومة.
- لا توضع قواعد الأعمال في UI.

## 3.9 الحضور وإكمال الحصة
- حالات الحضور: حاضر، غائب، متأخر، بعذر، لم يسجل.
- سجل التعديل وسببه عند الحاجة.
- سير إكمال: حضور → ما تم شرحه → واجب → ملاحظات → إنهاء.
- حفظ محلي دون إنترنت وإظهار حالة المزامنة.
- حماية التاريخ من التعديل الصامت.

## 3.10 الواجبات
- كيان مستقل مرتبط بالطالب والحصة والمادة.
- الوصف وتاريخ الإسناد والاستحقاق والمرفقات الاختيارية والحالة والدرجة والملاحظات.
- عرض القادم والمتأخر والمنجز.
- فصل ملاحظات المدرس الداخلية عن المرئية للأهل.
- تذكير بالمتابعة عند تفعيل القواعد.

## 3.11 الاختبارات والتقييمات والنتائج
- Assessment Engine مستقل عن Google Forms.
- تقييم يدوي ودرجة وملاحظات.
- النتيجة ترتبط بالطالب والتقييم والمادة والسياق والتاريخ.
- سجل تطور النتائج وتقارير الطالب/المادة/المجموعة.
- استيراد اختياري من Google Forms عبر Adapter والتحقق من الهوية ومنع التكرار.
- Google Forms ليس قاعدة النتائج الأساسية.

## 3.12 التذكيرات والإشعارات
- Reminder Engine مستقل عن UI وقناة الإرسال.
- تذكير يومي للتحضير، وقبل الحصة (خيارات 15/30/60/120 دقيقة حسب الإعداد)، والتحرك، والواجب، والاختبار، والدفع، والمهام.
- سجل إشعارات وحالاتها ومنع تكرار التسليم.
- تعديل/إلغاء الحصة يلغي أو يعيد جدولة تذكيراتها، مع فحص صلاحيتها قبل التسليم.
- قنوات: داخل التطبيق، PWA/محلية، بريد، WhatsApp، ومزودون مستقبلًا.
- توثيق قيود Android والمتصفح؛ لا يُضمن إشعار بعد إغلاق التطبيق دون آلية خارجية مختبرة.
- Calendar إسقاط اختياري لا مصدر الحقيقة للجدول.

## 3.13 بوابة ولي الأمر
- واجهة معزولة عن تطبيق المدرس.
- دخول/تفعيل آمن، قائمة الأبناء، التبديل بينهم.
- عرض الجدول والحصص والشرح والحضور والواجبات والنتائج المسموح بها.
- تحقق خادمي من العلاقة في كل طلب.
- عدم إرسال الملاحظات الداخلية.
- رموز تنتهي ويمكن إبطالها، وحدود محاولات.
- لا تعتمد الحماية على الواجهة وحدها.

## 3.14 الماليات والتقارير
- سعر الحصة، الاشتراك/الباقة، المدفوع والمتبقي، الخصم والاسترداد والحصة المجانية.
- وحدة مالية مستقلة وصلاحيات منفصلة؛ لا يشترط نظام محاسبة متقدم أو رواتب في V1.
- تقارير طالب، مادة، مجموعة، حضور، واجبات، نتائج، منهج، نشاط مدرس، وماليات أساسية عند تفعيلها.
- طباعة/تصدير وفق الصلاحيات.

## 3.15 قاعدة البيانات والعمل دون إنترنت
- IndexedDB خلف Adapter؛ لا تتعامل الواجهة معها مباشرة.
- Repositories وخدمات تطبيق مستقلة.
- معاملات ذرية للعمليات المهمة وترحيلات schema مرقمة ومختبرة.
- التشغيل المعتاد من البيانات المحلية، لا تنزيل كل Sheets عند كل فتح.
- حفظ التغييرات محليًا وإظهار حالتها: محلية/تنتظر المزامنة/مزامنة/تعارض/تحتاج معالجة.
- معالجة فشل التخزين والامتلاء وفقد بيانات المتصفح.
- لا نجاح زائف عند فشل الحفظ.

## 3.16 المزامنة والتعارضات
- Outbox/Offline Queue، معرفات مستقرة، سجل تغييرات ومراجعات واضحة.
- `operationId` مرتبط ببصمة الحمولة؛ إعادة استخدامه بحمولة مختلفة ترفض بـ`IDEMPOTENCY_KEY_REUSE`.
- فصل `serverRevision` عن `client committedRevision`.
- إعادة محاولة آمنة، واستئناف بعد انقطاع، ومنع تكرار الأثر.
- حل تعارضات حسب نوع الكيان.
- `organizationId` مصدره موثوق في الخادم، وليس قيمة يقررها العميل.
- المزامنة ليست نسخة احتياطية.

## 3.17 النسخ والاستعادة والاستيراد والتصدير
- سياسة النسخ ومكانه وتواتره وصلاحياته.
- تضمين إصدار schema والتحقق من سلامة النسخة.
- اختبار استعادة حقيقي، لا مجرد وجود ملف.
- منع الاستعادة فوق منشأة أخرى.
- كشف النسخة التالفة وغير المتوافقة.
- استيراد/تصدير يتحقق من الإصدار والحقول والتكرار والصلاحيات.
- توضيح حدود التخزين المحلي.

## 3.18 الترخيص والتثبيتات
- فصل License عن User/Device/Installation/Organization.
- الحفاظ على التوقيع والتشفير المعتمدين وعدم إعادة اختراعهما بلا سبب.
- عدم كشف المفتاح الخاص في تطبيق العميل.
- حالات التفعيل والانتهاء والتعطيل والنقل وحدود الأجهزة.
- `Entitlements` للمزايا حسب الإصدار.
- انتهاء الترخيص لا يتلف بيانات المستخدم.
- الترخيص ليس بديلًا للمصادقة والتفويض.
- توثيق حدود الحماية الواقعية.

## 3.19 الأمن والخصوصية
- عدم الثقة في العميل وحده للقرارات الحساسة.
- سرية رابط Apps Script ليست حماية.
- تحقق خادمي من الهوية والمنشأة والدور والعلاقات.
- تحقق المدخلات، تحديد معدل الطلبات، حماية الرموز، وسجل تدقيق.
- سياسة حذف وأرشفة وخصوصية واحتفاظ.
- عدم تسجيل الأسرار أو بيانات حساسة.
- عدم رفع بيانات طلاب حقيقية أو مفاتيح إلى GitHub.
- عزل بيانات المنشآت والأسر.

## 3.20 تكاملات Google وPWA والأداء
- Apps Script API/Adapter وليس بديلًا عن Domain.
- Sheets للتخزين/التزامن عبر مستودعات، لا اتصال مباشر من UI.
- Drive للمرفقات والنسخ، Calendar لإسقاط المواعيد، Gmail للتنبيهات، Forms لاستيراد نتائج اختياري.
- إعدادات مركزية وروابط قابلة للتكوين.
- التعامل مع الحصص والأخطاء وإعادة المحاولة وفشل المزود دون تعطيل المحلي.
- PWA manifest وأيقونات وتثبيت Android وService Worker للكاش/التحديث فقط.
- منع خلط نسخ قديمة وجديدة عند التحديث.
- قياس الأداء فعليًا على الهاتف وبيانات اختبار اصطناعية.
- تشخيص موحد ورسائل عربية وتصنيف للأخطاء وفحص صحة الخدمات.

## 3.21 التوسعات المستقبلية
- مركز تعليمي متعدد المدرسين والموظفين.
- ذكاء اصطناعي اختياري مع حماية الخصوصية والتكلفة.
- WhatsApp وقنوات اتصال أخرى عبر Adapters.
- خرائط ومسارات متقدمة.
- بحث/أوامر عامة.
- Marketplace والدفع الإلكتروني وNative App ليست شروط V1 ولا تُضاف إلا بقرار نطاق مستقل.
- الوظائف الأساسية لا تعتمد على Google Forms أو Maps أو Email أو WhatsApp أو AI.

# 4. البنية التقنية والقرارات الثابتة

الهيكل المرجعي في اللقطة الحالية:
- `packages/domain`: كيانات وقواعد مجال نقية.
- `apps/web`: تطبيق المدرس PWA.
- `apps/portal`: بوابة ولي الأمر.
- `apps/script`: API/خدمات Google Apps Script.
- `tests`: اختبارات.
- `docs/architecture`: قرارات ووثائق.
- GitHub Actions للبناء والنشر بعد التحقق.

قواعد لا تُكسر:
1. UI → Application Services → Repositories → Local DB Adapter.
2. لا اتصال مباشر من الواجهة إلى Sheets.
3. لا منطق أعمال في UI أو Service Worker.
4. Domain لا يعتمد على DOM أو IndexedDB أو Google APIs.
5. كل خدمة خارجية خلف Adapter.
6. Sync منفصل عن Backup.
7. فصل الهوية والحساب والمنشأة والتثبيت والجهاز والترخيص.
8. كل تغيير schema يحتاج Migration.
9. تغييرات API/Domain/DB تتطلب تحديث العقود والاختبارات.
10. لا يعاد فتح مرحلة مغلقة إلا بسبب تناقض حقيقي موثق، مع أقل تعديل ممكن.

# 5. الحالة الواقعية للملفات التي فُحصت سابقًا

## الموجود بحسب الفحص السابق
- هيكل Monorepo مبدئي.
- `apps/web/index.html` وواجهة Preact مبدئية في `apps/web/src/main.tsx`.
- IndexedDB أولية باسم `jihad_meta` وبها `installation` و`_kv` فقط؛ ليست قاعدة التطبيق الكاملة.
